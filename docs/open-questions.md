# 設計の決定記録

v0.1 を決めるまでに検討したことと、その結論。まだ決めていないことは末尾の「残っている課題」にまとめる。

## 決定したこと

| # | 論点 | 決定 | 理由 |
| --- | --- | --- | --- |
| Q1 | アプリの構造 | TEA。状態は Model 一つだけ | 状態の流れが一本で追える。hooks は純粋さを壊す |
| Q2 | 型クラス | 組み込みの 5 つ（`Num` `Ord` `Show` `Append` `Child`）だけ | ユーザー定義を許すと、辞書渡しの実装とエラーメッセージが重くなる |
| Q3 | 評価戦略 | 正格 | JS への変換が素直で、デバッグしやすい |
| Q4 | JSX に `String` を埋め込めるか | `Child` クラスで `String` も書ける。`Int` は `show` が必要 | 暗黙の変換は型の読みやすさを損なう |
| Q5 | props のデフォルト値 | 定数式だけ | |
| Q6 | スプレッド属性 `{...props}` | 入れない | 書き方が二つになる |
| Q7 | React 部品を使うか | 使わない | 純粋さと型の保証を優先する |
| Q8 | ランタイム | 自前の仮想 DOM | 依存がなく、小さい |
| Q9 | コンパイラの実装言語 | TypeScript | 出力先が JS。ブラウザでも動かせる |
| Q10 | 拡張子 | `.lx` | |
| Q11 | レイアウト部品 | `Row` `Column` `Grid` `Stack` `Scroll` `Spacer` | `Stack` で重ね合わせ（Q16）も扱う |
| Q12 | `case` / `let` / `if` / ラムダ | すべてなくす | 等式・ガード・`where` で書ける。書き方を一つにする |
| Q13 | JSX の `{}` に書ける式 | 名前・リテラル・フィールド・1 段の関数適用だけ。演算子も不可 | タグには名前だけを書く |
| Q14 | 見た目の書き方 | `Style` 値を `where` に書く。CSS・`class`・margin はなくす | 新しい仕組みを足さず、レコードとガードで書ける |
| Q15 | リストの描画 | `{map item xs}`。専用構文は作らない | `where` で要素の部品に名前がつく |
| Q16 | 重ねて表示する部品 | `<Stack>` | |
| Q17 | 1 ファイルの部品の数 | いくつでも定義できる。外部に公開するのはモジュール名と同じ主部品だけ | 外からは 1 ファイル 1 部品、中では小さな部品を自由に作れる |
| Q18 | ユーザー定義の演算子・`$` | なし | 書き方を一つにする |
| Q19 | 色や大きさの指定 | デザイントークンの名前だけ。数値は `Px` のみ | 見た目のばらつきを防ぐ |

## 残っている課題

| 論点 | 内容 |
| --- | --- |
| サブスクリプション | タイマーやキーボード入力など、外から届くイベントをどう受け取るか（Elm の `Sub`） |
| 部品ごとの状態 | フォームやダイアログが増えたとき、Model の配線がつらくならないか。実際のアプリで確かめる |
| テーマ | トークンの実際の値（色・ピクセル数）をユーザーが変える方法 |
| レスポンシブ | 画面の幅で `Row` と `Column` を切り替える方法 |
| ルーティング | URL と画面の対応 |
| `Style` に足すフィールド | アニメーション、グラデーション、文字の装飾など。必要になったものから足す |
