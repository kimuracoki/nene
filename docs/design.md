# 設計の考え方

## なぜ作ったか

Elm で小さなアプリを作ってみて、型があって実行時エラーがほとんど起きない安心感はとても良かった。一方で、書いていて気になるところもあった。

- 場合分けが `case` と `let ... in` だけで、Haskell のように等式・ガード・`where` で書けない。
- `div [ class "row" ] [ ... ]` の形だと、画面の形が見えにくい。
- 横に並ぶか縦に並ぶかが CSS の中にあって、コードを見ても画面が想像できない。
- 部品に省略できる引数がなく、呼び出すたびに全部書くことになる。

Nene は、Elm の安心感はそのままにして、Haskell の書き心地と JSX の見やすさを持ち込むために作った。

## 名前

Nene（ネネ）は、ハワイにだけいるガンの名前。祖先は水辺で暮らす鳥だったが、溶岩の島に渡って陸で暮らすうちに、水かきは半分ほどに小さくなり、代わりにごつごつした地面を歩ける脚を手に入れた。

この言語も同じ道をたどっている。Haskell の系譜から UI という陸地に来て、`case` や `let`、ラムダは手放した。代わりに、並び方を表すタグと JSX を手に入れた。規則は少なく、一つに絞る。全体の形は、タグを見ればそのまま分かる。

**Simple rules. Beautiful structures.**

## 4 つの原則

### タグを見れば、画面の形が分かる

HTML が「文書の構造」を表すものだったのは、テキスト中心のサイトの時代の話だと思う。アプリの画面で知りたいのは、何がどう並んでいるかだ。だから並び方は CSS ではなく、タグで書く。

```haskell
<Row gap={S}>
  <Photo />
  <Photo />
</Row>
```

SwiftUI の `HStack`、Flutter や Compose の `Row` と同じ考え方。

### タグには名前だけを書く

タグの属性に長い式や条件が並ぶと、画面の形が読めなくなる。そこで、JSX の `{}` に書けるのは名前やフィールド、1 段の関数呼び出しだけにした。計算や分岐は `where` に書く。

```haskell
<li class={look}>{todo.title}</li>
  where
    look
      | todo.done = css.done
      | otherwise = css.item
```

上半分を読めば画面の形が、下半分を読めば細かいことが分かる。見た目も同じで、タグには `css.done` のような名前だけを置き、中身はファイル末尾の `style` ブロックに普通の CSS で書く。

### 書き方は一つ

同じことを書く方法がいくつもあると、読むたびに頭を切り替えることになるし、チームで書き方がばらつく。React で CSS を当てる方法（CSS ファイルの読み込み、CSS-in-JS、`style` 属性、props）がその例だと思う。CSS そのものが悪いのではなく、当て方が多すぎる。

だから、同じことができるものは片方を削った。

| ないもの | 代わりに使うもの |
| --- | --- |
| `if` `case` `let` ラムダ | 等式・ガード・`where` |
| CSS の当て方の選択肢 | `style` ブロックと `class={css.名前}` の一つだけ |
| `$` やユーザー定義の演算子 | 括弧 |
| スプレッド `{...props}` | 属性を 1 つずつ書く |

新しい機能を足すときも、まず今ある仕組みで書けないかを考える。たとえば部品の省略できる属性は、「デフォルト値つきのレコード」というレコードの機能として入れた。アプリの設定（`App.app` に渡すもの）も同じ仕組みで省略できる。

### 型が通れば、実行時エラーは起きない

Elm の一番良いところなので、ここは譲らない。`null` はなく `Maybe` を使う。パターンの漏れはエラーにする（警告ではない）。部品の属性も、HTML の属性も型で検査する。

## アプリの形

状態はアプリ全体で 1 つ（Elm と同じ）。部品ごとに状態を持つ React の形は便利だが、状態の流れが追いにくくなる。

Elm と違うのは、副作用を `update` から返さないこと。`update` はいつも「メッセージで状態がどう変わるか」だけを書き、外の世界に何かをするときは `effect` という別の関数に書く。

```haskell
update :: Msg -> Model -> Model
effect :: Msg -> Model -> Cmd Msg
```

小さなアプリは `App.app { init, update, view }` だけで書け、必要になったら `effect`・`subscriptions`・`onUrlChange` を足していく。

## 見た目

並び方はタグで、見た目は CSS で書く。CSS は誰もが知っていて、できることも多い。新しい書き方を覚えてもらうより、CSS をそのまま使える方がいい。

その代わり、当て方は一つに絞った。部品のファイルの末尾に `style` ブロックを書き、タグには `class={css.card}` と名前だけを書く。`style` ブロックはそのファイルのタグにだけ効くので、部品の見た目はその部品の中で閉じる。書いていないクラスを使えばコンパイルエラーになる。

色を変えたいときも、専用の仕組みは作らず、CSS 変数で決める。

狭い画面への対応は、多くの場合「横に並んでいたものを縦にする」で足りるので、`<Row collapse={M}>` の 1 つだけにした。

## 外とのやりとり

Elm でいちばん手間だったのは、JSON のデコーダーを型とは別に書くことだった。型にもう書いてあることを、もう一度書かされる。

Nene では、JSON との変換を型から決める。メッセージに `GotTodos (Result Http.Error [Todo])` と書けば、`Http.get` はそのとおりに JSON を読む。合わなければ、どこが違ったかを添えて `Err` で返すので、実行時エラーにはならない。変換の規則は 1 つだけにして、フィールド名を付け替えるような設定は持たない。

## 部品ごとの状態を持たない

React の `useState` のような、部品ごとの状態は入れなかった。入れると、同じ値を Model にも部品にも置けるようになり、「どちらに置くか」で迷う。アプリの状態が Model を見れば全部分かる、という性質もなくなる。

Elm で部品の状態がつらいのは、ドロップダウンの開け閉めのような、アプリにとってはどうでもいい状態まで Model に配線することだと思う。そういう見た目だけの状態は、今のブラウザが持てる。`popover` 属性を付けた要素は押せば開き、外を押せば閉じる。`<details>` は開け閉めを覚えている。そこで、アプリが知る必要のある状態は Model に、見た目だけの状態はブラウザに、と分けた。`nene-lang-ui` の Menu・Popover・Accordion・Tooltip は、この形で作ってある。

## 何を言語に入れ、何を外に出すか

ルーティング、HTTP、JSON は標準ライブラリに入れ、差し替えられないようにした。React ではルーターも状態管理もスタイルの当て方も選べるが、そのぶん、プロジェクトごとに書き方が違う。Nene では、こうした土台は一通りだけにする。標準ライブラリに入れても、使っていないモジュールは出力に入らないので、アプリは重くならない。

見た目の好みが分かれる部品集は、別のパッケージ `nene-lang-ui` にした。使わずに自分で部品を作ってもよい。ただし、外から足せるのは部品と関数だけで、言語の振る舞いを変える差し込み口は作らない。

## 道具

`nene` コマンド 1 つで、作成・開発・ビルド・公開前の確認・型検査・エディタ連携まで済む。公開先がサブディレクトリでも、`--base` を付けるだけでコードは書き換えない。エラーは該当する行に印を付けて見せる。`view` は model から画面を作るだけの関数なので、ビルドのときにページを HTML にしておける（静的生成）。設定はいらず、リンクをたどってページを見つける。設定ファイルは必要なく、入口は `index.html` に書いた `.nn`、画像などは `public/` に置く。特別なことをしたいときだけ、普通の Vite の設定を書ける。

コマンド・Vite プラグイン・言語サーバーは同じコンパイラを使うので、エディタで出るエラーとビルドで出るエラーは必ず一致する。
