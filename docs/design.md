# 設計の考え方

## なぜ作ったか

Elm で小さなアプリを作ってみて、型があって実行時エラーがほとんど起きない安心感はとても良かった。一方で、書いていて気になるところもあった。

- 場合分けが `case` と `let ... in` だけで、Haskell のように等式・ガード・`where` で書けない。
- `div [ class "row" ] [ ... ]` の形だと、画面の形が見えにくい。
- 横に並ぶか縦に並ぶかが CSS の中にあって、コードを見ても画面が想像できない。
- 部品に省略できる引数がなく、呼び出すたびに全部書くことになる。

Tufa は、Elm の安心感はそのままにして、Haskell の書き心地と JSX の見やすさを持ち込むために作った。

## 名前

Tufa（トゥファ）は、石灰華という岩の名前。湧き水に溶けた石灰が、少しずつ積み重なってできる。従っている規則は単純なのに、段々の棚や枝分かれした柱のような、複雑で美しい形が育つ。

この言語でやりたいことも同じで、規則は少なく、一つに絞る。その少ない規則で小さな部品を書き、積み重ねて画面にする。全体の形は、タグを見ればそのまま分かる。

**Simple rules. Beautiful structures.**

## 4 つの原則

### タグを見れば、画面の形が分かる

HTML が「文書の構造」を表すものだったのは、テキスト中心のサイトの時代の話だと思う。アプリの画面で知りたいのは、何がどう並んでいるかだ。だから並び方は CSS ではなく、タグで書く。

```haskell
<Row gap={S}>
  <Photo />
  <Photo />
</Row>
```

SwiftUI の `HStack`、Flutter や Compose の `Row` と同じ考え方。

### タグには名前だけを書く

タグの属性に長い式や条件が並ぶと、画面の形が読めなくなる。そこで、JSX の `{}` に書けるのは名前やフィールド、1 段の関数呼び出しだけにした。計算や分岐は `where` に書く。

```haskell
<li class={look}>{todo.title}</li>
  where
    look
      | todo.done = css.done
      | otherwise = css.item
```

上半分を読めば画面の形が、下半分を読めば細かいことが分かる。見た目も同じで、タグには `css.done` のような名前だけを置き、中身はファイル末尾の `style` ブロックに普通の CSS で書く。

### 書き方は一つ

同じことを書く方法がいくつもあると、読むたびに頭を切り替えることになるし、チームで書き方がばらつく。React で CSS を当てる方法（CSS ファイルの読み込み、CSS-in-JS、`style` 属性、props）がその例だと思う。CSS そのものが悪いのではなく、当て方が多すぎる。

だから、同じことができるものは片方を削った。

| ないもの | 代わりに使うもの |
| --- | --- |
| `if` `case` `let` ラムダ | 等式・ガード・`where` |
| CSS の当て方の選択肢 | `style` ブロックと `class={css.名前}` の一つだけ |
| `$` やユーザー定義の演算子 | 括弧 |
| スプレッド `{...props}` | 属性を 1 つずつ書く |

新しい機能を足すときも、まず今ある仕組みで書けないかを考える。たとえば部品の省略できる属性は、「デフォルト値つきのレコード」というレコードの機能として入れた。アプリの設定（`App.app` に渡すもの）も同じ仕組みで省略できる。

### 型が通れば、実行時エラーは起きない

Elm の一番良いところなので、ここは譲らない。`null` はなく `Maybe` を使う。パターンの漏れはエラーにする（警告ではない）。部品の属性も、HTML の属性も型で検査する。

## アプリの形

状態はアプリ全体で 1 つ（Elm と同じ）。部品ごとに状態を持つ React の形は便利だが、状態の流れが追いにくくなる。

Elm と違うのは、副作用を `update` から返さないこと。`update` はいつも「メッセージで状態がどう変わるか」だけを書き、外の世界に何かをするときは `effect` という別の関数に書く。

```haskell
update :: Msg -> Model -> Model
effect :: Msg -> Model -> Cmd Msg
```

小さなアプリは `App.app { init, update, view }` だけで書け、必要になったら `effect`・`subscriptions`・`onUrlChange` を足していく。

## 見た目

並び方はタグで、見た目は CSS で書く。CSS は誰もが知っていて、できることも多い。新しい書き方を覚えてもらうより、CSS をそのまま使える方がいい。

その代わり、当て方は一つに絞った。部品のファイルの末尾に `style` ブロックを書き、タグには `class={css.card}` と名前だけを書く。クラス名はファイルごとに自動で区別されるので、ほかの部品とぶつからない。書いていないクラスを使えばコンパイルエラーになる。

色を変えたいときも、専用の仕組みは作らず、CSS 変数で決める。

狭い画面への対応は、多くの場合「横に並んでいたものを縦にする」で足りるので、`<Row collapse={M}>` の 1 つだけにした。

## 道具

`tufa` コマンド 1 つで、作成・開発・ビルド・型検査・エディタ連携まで済む。設定ファイルは必要なく、入口は `index.html` に書いた `.tufa`、画像などは `public/` に置く。特別なことをしたいときだけ、普通の Vite の設定を書ける。

コマンド・Vite プラグイン・言語サーバーは同じコンパイラを使うので、エディタで出るエラーとビルドで出るエラーは必ず一致する。

## これから

- 部品の中だけで完結する状態（ドロップダウンの開閉など）を、Model に配線せずに持てるようにしたい。純粋さを保ったまま、どう書けるかを考えている。
- サーバーとの通信と、JSON を型付きの値にする方法。
- `style` ブロックの CSS も、エディタで補完や検査ができるようにしたい。
